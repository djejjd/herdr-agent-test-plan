# 测试与独立Review
状态: active  
创建: 2026-11-25  
最后更新: 2026-11-25  
关联: ../README.md

测试者先写出一条“无论如何都应成立”的行为，再设计能推翻它的例子。例如“同一任务只提醒一次”。依次试正常投递、重复投递、两条消息乱序、确认前掉线、重连后重放。记录输入、期望、实得、代码版本以及证据来自真实 harness 还是 fixture。

按改动风险选取边界、超时、权限、部分成功、取消、并发、旧数据和资源释放场景。无法验证的写明原因和影响。修复前让回归测试暴露旧行为；修复后重跑该测试、相邻路径和项目既有检查。

每轮 Review 锁定提交和检查问题。把新发现分成阻塞缺陷、独立后续项、待裁决取舍。相同发现沿用编号。修复后的审查聚焦该差异以及可能受影响的行为。满足验收条件、阻塞项清零、剩余风险有明确归属即可收尾；审查无需为了交件而发明新问题。

## 给独立验证者的派工示例

交给验证者 U2 的原话、用户入口和待审版本，让他自行挑选能推翻“仅导出可见行”的输入。例如载入 A、B，筛选后只显示 A，打开导出文件核对内容；随后清除筛选重试，检查上一次筛选是否残留。零匹配时，先验证文件中没有隐藏行；是否生成空文件属于另一项产品决定。

复审时记录发现在哪个版本首次出现。原版就违反 U2 的属于首轮遗漏，修复差异引入的属于回归，无关改进进入后续项。主管按这三类安排下一步。对同一提交，已覆盖的行为保留证据；只有改动或新的失败假设触及该行为时才重新验证。
