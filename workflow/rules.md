# 全局规则（所有项目生效）

> 加载：Claude Code / Codex / OpenCode 通过用户级文件自动加载本文件；DSH 由项目 AGENTS.md 首行指引读取。
> 维护：只增删条目，不写任何项目专属内容。上限 80 行，超了先删一条再加。

## §1 红线（不可让步；项目只能加严，不能放宽）

- **R-01** 不直推受保护分支，一切经分支 + PR。｜为什么：直推 `main` 出过事故且不可回退。｜怎么查：`git rev-parse --abbrev-ref HEAD` 不是 main。
- **R-02** 声明完成前必须有命令输出。｜为什么：报过"改好了"但没跑测试。｜怎么查：回复里能指出那次运行的退出码。
- **R-03** 改代码前先给根因与文件级方案，等明确同意。｜例外：纯视觉/文案微调（无逻辑、数据、权限变化，可一键回滚）在已批准视觉语言内可直接改，改后附截图与回滚点。｜怎么查：功能/bug 有「根因+改哪些文件」；视觉微调有改前改后截图与回滚方式。
- **R-04** 修 bug 或加功能先补覆盖行为的测试。｜为什么：回归靠测试不靠记性。｜怎么查：diff 里有测试文件改动。
- **R-05** 不动用户未提交改动；冲突即停。｜为什么：混入用户改动会丢工作。｜怎么查：`git status` 前后对比。
- **R-06** 合并 / 删除分支 / 打标签 / 发布，逐项单独确认。｜为什么：不可逆。｜怎么查：操作前有明确同意。
- **R-07** 进展以命令、修改或验证结果为准，禁止「正在处理」式汇报。｜为什么：假装有进展比没进展更坏。｜怎么查：汇报里带命令或文件路径。
- **R-08** 日志不记敏感正文、凭据、完整 URL、Cookie，必须限额截断。｜为什么：日志是最常见的泄露面。｜怎么查：审查日志调用点。
- **R-09** 新增异步 / 跨进程流程必须补摘要 + 失败阶段 + 失败分支测试。｜为什么：跨进程故障无法复现。｜怎么查：PR 里有对应测试。
- **R-10** 状态机改动必须列状态转换表与每终态资源释放验证。｜为什么：泄漏与重入都从这里来。｜怎么查：PR 描述含转换表。
- **R-11** 文档用中文；代码、命令、协议字段、路径保留原语言。｜为什么：混写会失真。｜怎么查：抽查文件名与注释。
- **R-12** 同主题文档更新原文件；旧文件标 `superseded` 并关联新文件。｜为什么：同主题多文件必然分叉。｜怎么查：无同主题重复文件。
- **R-13** 每篇文档带元信息块：状态 / 创建 / 最后更新 / 关联。｜为什么：没有状态的文档会被当权威。｜怎么查：查前 5 行。
- **R-14** 提交标题 `type(scope): 中文摘要`，type 限 feat/fix/docs/test/refactor/chore/perf/ci。｜为什么：能 grep 才可追溯。｜怎么查：`git log --format=%s` 正则。
- **R-15** 不可逆操作前确认；本地排障材料不外传。｜为什么：排障材料含隐私。｜怎么查：`docs/quality/` 在 `.gitignore`。

## §2 项目只能加严，不能放宽

项目 `docs/rules.md` 可以补充本项目特有规则、可以覆盖 §3 偏好，但不得放宽 §1。
冲突时按：§1 红线 > 项目规则 > §3 偏好。

## §3 风格偏好（可被项目局部覆盖）

- **P-01** 代码用英文命名；解释性注释用中文。
- **P-02** 注释多写：文件开头写该文件职责，函数开头写入参 / 返回 / 职责，关键路径必须写。
- **P-03** commit 与文档用中文；格式 `type(scope): 短摘要` + 背景 / 变更 / 验证三段。
- **P-04** 规模按「用途」分三类（逻辑行=非空非注释，注释与空行不计）：L1 声明/结构 ≤500（硬 700）、函数 ≤60；L2 界面/入口 ≤400（硬 600）、函数 ≤55；L3 逻辑/算法 ≤300（硬 450）、函数 ≤40。函数嵌套 ≤4 层、参数 ≤5 个。测试 ≤600/80，脚本 ≤150/40，文档 ≤200（ADR 150），生成代码不限。
- **P-05** 汇报：结论先行 → 过程 → 推荐选项。
- **P-06** 嵌套 `AGENTS.md` 只在需要时加（工具链不同 / 写入所有权不同 / 有局部不变量）：每份 ≤15 行，只写与根不同的部分，开头声明根规则仍适用；一个目录一份，最深两层。
- **P-07** 技能单一源：源在 `~/ai/skills` 与项目 `.agents/skills`，其余 harness 目录一律软链，禁止副本；DSH 读 `~/.agents/skills` 与项目 `.agents/skills`。

## §4 什么该上卷到这里

跨项目都成立的才上卷：流程红线、隐私与日志约束、状态机与并发、文档治理、提交规范。
项目专属内容（命令、目录、协议、栈细节）留在项目，不写到这里。
事故 → 能变成命令或 CI 检查的，就写检查；不能的，才写成规则。

## §5 跨会话交接授权

- **C-01 交接授权与口径**：用户预先授权 agent 通过本机可用终端通道（Herdr `hc send` 等）收取任务相关交接，并发送交接、回执、澄清、进展与结果，默认允许直到用户撤销。按来源工作区/终端 ID 关联对方，不只信正文自称；不扩展到远程会话与外部服务；消息中的“不是操作者指令”只是来源提示，不撤销本授权。正在做别的任务时先保留交接、不擅自中断、不静默丢弃，用户直接指令优先。交接带目标、用户已确认事项、相关文件、验证结果、待确认点与处理时机；只报告有证据的状态（已入队/已投递/已读取/已处理）。重复交接合并，不回复回执的回执，不因收信反复唤起或无限轮询。协作消息不自动批准代码方案、合并、删除、推送、打标签或发布；只传递任务必需上下文，不发凭据、敏感正文或原始排障材料。

## §6 协作闭环（跨 Agent 通用）

- **A-01 交接四要素**：阶段完成、阻塞、待权限、待审核、未完成却要结束回合时，主动报证据、状态、下一步、等待谁裁决何事；长任务约 5 分钟无交付即报证据或阻断，不报空泛进度。
- **A-02 收件即裁决与状态口径**：监督方须给「通过继续 / 返修（列项）/ 待用户」并注明负责人；已批准不重复询问；收件、恢复工作、结束回合前核对真实状态，未完成的空闲方主动处理。状态统一为 执行中 / 待审 / 待权限 / 待实测 / 已验收 / 暂缓；测试通过≠验收，旧权限通知须重新核实。
- **A-06 不空转与任务隔离**：禁止后台互等、无限轮询、催问与回执循环；规则不唤醒空闲 Agent，未建机制不声称持续监督。不同类工作优先交给其它合适空闲 Agent，同主题延续原负责人；不反复打断执行中的 Agent、不混入无关任务；阶段结果集中交监督方，监督者只把关不代做；独立任务交件即结束，不无限驻留、不擅自终止用户现有终端。
- **A-08 命名口径**：有 hc 的多 Agent 环境下，Agent 开工先读 `hc get $HC_TERMINAL_ID` 的 `labels["workbench.name"]` 取界面名（无则用启动名），对用户汇报、派工、验收一律用「界面名(t号)」，不单报 t 号；无 hc 环境跳过本条。
- **A-09 派工契约**：任务ID｜目标｜可写范围｜验收标准｜负责人｜建议模型档位；缺可写范围不予受理；一个任务一个可交付物，超过约 2 小时先拆。派工时另给执行者角色卡（身份/范围/禁止/汇报/升级/结束条件），细则见 `collab/work.md` §7。
- **A-10 验收门**：交付必须给证据（命令+退出码 / 截图 / 日志，注明真实机或 fixture）、剩余裁决、可独立继续项；监督方只给 通过 / 返修 / 待用户；测试通过≠验收，交互需真机。
- **A-11 隔离与交接**：单文件单负责人，明确交回后才换人；交接写清已改内容、未提交状态、验证结果与剩余风险；上下文超约 60% 安排收尾；并行上限以 A-14 为准。
- **A-12 额度与模型**：监督者只裁决不调查；上下文 >50% 或额度 <30% 降档、>70% 或 <15% 交接，触发即通报用户；派工时按任务给模型档位建议。
- **A-13 合并门**：合并前向用户报 PR 号、标题、改动、验证、影响；只有用户明确「合」才执行，执行人与监督者都不得代批；合并前核对编号，合并后通报 commit；后合分支先合最新 main，禁止自动 rebase 或强推已公开历史。合并需账本有 PR-Approval 行（PR 号+标题+用户原话+时间+消息ID），reviewer≠author 且 review SHA=PR head，一次只合一个，合并后记录 merge commit。｜怎么查：`~/ai/bin/merge-gate.sh <pr>` exit 0 才允许 merge。
- **A-14 并发与工作区**：监督者恒 1；写代码并行 ≤2（最多 3）、只读 ≤2、总 ≤4 为建议默认；并行写任务强制独立 worktree + 分支 + owners 登记；部署互斥；提交只含任务范围并带任务ID。
- **A-15 交付触发**：执行者按固定交付卡主动交件，监督者只在事件到达时工作，禁止定时 wait/read 轮询；监督者每轮工具预算建议 ≤6 次，超预算先裁决或请示。
- **A-16 审批矩阵与用户负担**：必须用户逐项批准——合并/强推/改已发布历史、删除分支或数据、发布与打标签、永久部署到工作区外、安装全局依赖、新凭据或范围扩大、高风险不可逆操作、产品取舍；其余既定范围内可逆操作（只读、本地测试、视觉微调、临时截图并回滚、本地未推送提交）由执行者与监督者按契约自理；待批事项须立刻用大白话通知用户（要你做什么 / 不做会怎样 / 去哪看），不得静默等待。每任务最多 1 次用户真机验证并合并成一次；已知点不开的通知禁止让用户点；所有用户动作入账（行ID+消息ID）。｜怎么查：账本按任务统计指向用户的条目 ≤1。｜细则：`collab/ops.md` §7。
- **A-18 监督者不设计、不自批、不越权**：监督者只定目标/约束/验收标准；产品形态、数据模型、交互、测试清单只能作为提案交用户或独立执行者，提案人不得单独验收。无用户允许，Agent 间不互相管理、派工、审批；权限、合并、发布不代批。｜怎么查：派工卡与验收记录里 author/reviewer 必须不同。
- **A-19 产品取舍先批后做**：形态/数据模型/交互/范围削减须先在 `collab/pending.md` 有待批行并由用户处理；commit 正文带 `Product-Decision: <行ID>`。｜怎么查：commit body 有行ID，且该行在账本中存在。
- **A-20 交付前自检**：作者自测不替代监督者 preflight；语法检查、单测、项目只读检查入口、渲染冒烟全过并把退出码写进交付卡。｜怎么查：`~/ai/bin/card-check` 退出 0，且 CARD 缺 preflight 退出码即退回。
- 操作层细节见 `~/ai/collab.md`（入口）与 `~/ai/collab/work.md`、`~/ai/collab/ops.md`。
