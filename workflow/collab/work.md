# 工作流：派工、交付、验收、合并

## 1. 派工契约

```
任务ID｜目标（可验收）｜可写范围｜验收标准（命令+期望输出+证据类型）｜负责人｜建议模型档位
```

- 六项缺一不受理；缺可写范围视为未定义任务，执行者可拒接。
- 一个任务一个可检查的交付物；超过约 2 小时先拆。

## 2. 交付卡（唯一交件格式）

```
CARD｜<任务ID>｜<界面名(t号)>｜<完成|阻塞|返修|待审>
EVIDENCE: cmd=`...` exit=<码>; file=<路径:行号>; shot=<图片路径>
RULING: 无 / 需批：<一项，含选项与默认>
NEXT: 无 / <可独立继续的一步>
```

规则：

- 首行固定前缀，便于 grep 校验；缺 EVIDENCE 直接退回。
- 证据必须可复核：命令+退出码、或文件:行号、或截图路径；注明真实机或 fixture。
- 大段输出不入卡，只给路径与一句结论。
- 阻塞卡必须写「等谁、等什么决定、我还能做什么」。

## 3. 证据分级与验收门

1. 已送达（send 返回）→ 2. 已接单（回执含任务ID）→ 3. 有物证 → 4. 通过验收。

- 监督者只给三种结论：**通过 / 返修（列项+文件+负责人）/ 待用户（写明待谁待什么）**。
- 测试通过 ≠ 验收；交互类必须真机；fixture 必须标注，禁止冒充实拍。
- 返修必须点名文件与验收项，不接受「再改改」。

## 4. 合并门

1. 合并前向用户报：PR 号、标题、改动、验证、影响。
2. **只有用户明确「合」才执行**；执行人与监督者都不得代批。
3. 合并前 `gh pr view <号>` 核对编号与标题，禁止凭记忆填号。
4. 合并后立即通报 merge commit；同一时间只允许一个合并动作。
5. 后合分支先合最新 main；禁止自动 rebase、禁止强推已公开历史；冲突由后合者解决并报告。
6. 任务ID写进 commit 正文；标题守 `type(scope): 中文摘要`。
7. 合并前跑 `~/ai/bin/merge-gate.sh <PR号>`：账本须有该 PR 的 PR-Approval 行（PR 号+标题+用户原话+时间+消息ID），reviewer≠author 且 review SHA=当前 head；exit 0 才可执行合并。

## 5. 反模式（交付类）

| 反模式 | 后果 | 替代 |
|---|---|---|
| 「已实现，等验收」无裁决项 | 双方空转 | 交付卡 + 明确裁决 |
| 自证完成 | 假进度 | 命令输出 |
| 散文式交件 | 监督者逐段找证据 | 固定卡片 |
| fixture 冒充实拍 | 结论失真 | 标注并真机补验 |
| 合并前不核对 PR 号 | 误合并、写错标题 | 先 view |

## 6. 待批通报（方案要用户拍板时）

出现要用户批准的事，**立刻**用大白话发一条，不攒着、不等着、不代批：

```
PENDING｜<任务ID>｜<一句话标题>
要你做什么：<一个动作>
我建议：<明确的推荐做法，不许写“看情况”>
理由：<一句话为什么>
主要代价：<时间 / 风险 / 影响面，尽量量化>
不批准会怎样：<后果>
去哪点：<哪个标签 / 哪一行>
默认：<不回就不动，或我继续做什么>
```

四项必填：**推荐、理由、主要代价、不批准的影响**。缺任何一项不算有效待批；
推荐必须是可执行的一个选项，代价要能估（分钟数、影响文件数、影响范围）。

- 同时登记到唯一账本 `~/ai/collab/pending.md`（表头、状态口径与解析约定见该文件）；执行者只读，监督方单写。
- 用户没回：执行者继续做不阻塞的部分；全被卡住就写「暂停原因」。
- 禁用词：验收门、证据分级、阈值、契约——直接说「点哪、批什么」。

## 7. 派工角色卡

派工时给每个执行者一份卡，固定八项：

```
身份：<界面名(t号)>
任务ID：<C-xx>
可写范围：<文件/目录>
验收标准：<命令+期望输出+证据类型>
禁止：越权、自行派工、合并、激活前台窗口、改范围外文件
汇报：CARD 卡（证据/待批/下一步）
升级：卡住找监督者，不直接找用户
结束：交卡即结束，不驻留、不轮询
```

- 独立 worktree：写入该目录 `AGENTS.md`，工具自动加载。
- 共享目录：放 `.tmp/collab/agents/<界面名>-<t号>.md`，派工消息里给路径并要求开工先读。

## 8. 多 Agent 交付前检查项

- 派工前冻结完整原需求 ID；交付输入必须与原需求分离，不得同源或通过软链接指向同一文件，不得靠缩小派工卡覆盖原需求。追加需求保留原清单；减范围须有用户明确决定与对应 ID。
- 方案通过且要求继续实施时，同一轮必须有接手人、下一步和结构化投递回执；评审结论本身不是派发凭据。已批准的范围不重复请示。
- 运行器必须提供实际 `model-response` 首响应证据；模型列表、进程创建或目录条目不等于接单。
- 交付前运行派工卡指定的项目只读检查入口；缺项、输入非法或证据不可读不得交件。监督者从原需求核对覆盖，不以测试数量代替需求完整性。
- 技术交付通过时仍须明确未验交互；原生截图和 `check` 不代表真实点击或完整验收。检查器只验证结构、可读性及可观察状态，证据内容由独立评审核对。
- 原四行 `CARD` 格式保持不变；`EVIDENCE` 引用需求覆盖、派发、首响应、资源退出与证据边界。
